# Aldenmoor

RPG médiéval sombre dans le navigateur, au tour par tour, inspiré de Dofus : trois classes (guerrier, assassin, magicien), combat en grille avec initiative, métiers de récolte et de fabrication, carte en monde ouvert, ville centrale (atelier, coffre, marché, portail vers les régions).

Réalisé avec React 18 et Vite. Déployé sur Vercel à chaque envoi sur `main`. La partie est sauvegardée dans le navigateur (IndexedDB), avec export / import en fichier.

## Lancer le jeu

```bash
npm install
npm run dev        # http://localhost:5173
```

`npm run build` construit la version de production, `npm run preview` la sert en local.

## Tests

```bash
npm test           # validation des données + tous les tests (scripts/test-*.js)
npm run check      # tests puis build : à lancer avant d'envoyer
npm run test:ui     # test d'interface : joue un parcours complet dans un vrai navigateur (demande Playwright, voir scripts/test-ui.mjs)
```

Les tests sont de simples scripts Node, sans bibliothèque. GitHub les relance à chaque envoi (`.github/workflows/ci.yml`).
`node scripts/simulate-combat.js 200 5` simule des combats pour équilibrer (200 combats, niveau 5).
`node scripts/simulate-economy.js` donne le bilan de l'économie : or et drops par combat, revenu des récoltes, coût des sets, prix des agrandissements du coffre. Règle imposée par `test-economy.js` : dans un combat, l'or pur doit faire 25 à 55 % du revenu (à respecter pour chaque nouvelle région).

## Organisation du code

| Dossier | Contenu |
| --- | --- |
| `src/data/` | Toutes les données du jeu : classes, armes, objets, ressources, recettes, monstres, cartes. On équilibre ici, sans toucher à la logique. |
| `src/combat/` | Moteur de combat (sans React, déterministe avec une graine). |
| `src/utils/` | Logique pure : stats, progression, récolte, fabrication, coffre, raffinage, hôtel des ventes (annonces des joueurs simulés et les tiennes, prix fixés par les joueurs, taxe de mise en vente de 10 %, achat sans taxe), quêtes du jour et réputation de la ville, déplacements et chemins, sauvegarde. |
| `src/hooks/` | `usePlayer` : l'état du joueur et ses actions. |
| `src/components/` | L'affichage : `character`, `combat`, `map`, `forge`, `city`, `layout`, `shared`. |
| `src/sim/` | Joueurs simulés (500 aventuriers aux rôles variés, vie en ville, discussion). **Désactivés** : interrupteur `SIM_PLAYERS` dans `src/sim/config.js`. |
| `api/` | Route `/api/chat` (fonction Vercel) qui fait parler les simulés avec un modèle de langage. Inutile tant que les simulés sont désactivés. |
| `scripts/` | Tests, validation des données, simulation de combat, génération des feuilles d'animation. |
| `public/assets/` | Images : héros animés, monstres, icônes, décors, bâtiments. |

Règle de base : la logique vit dans `src/utils`, `src/combat` et `src/data` (testable sans navigateur) ; les composants ne font que l'afficher.

## Données sauvegardées

Base IndexedDB `aldenmoor`, magasin `kv`, clé `save` (texte JSON) : `{ version, savedAt, player, world }`. Le chargement est asynchrone (écran « Chargement… » un instant). Le localStorage (clé `aldenmoor:save`) ne sert plus que de **reprise** d'une ancienne sauvegarde (recopiée dans l'IndexedDB, relue pour vérifier qu'elle est identique, et seulement ensuite effacée : jamais de perte), de **filet** à la fermeture de la page (l'écriture IndexedDB n'y est pas garantie, la copie est reprise au chargement suivant) et de **repli** si l'IndexedDB est indisponible. La copie la plus récente gagne. Les écritures sont regroupées (seule la dernière compte) et ne bloquent plus le jeu. `test-save.js` vérifie tout cela. En changeant la forme d'une sauvegarde, augmenter `version` dans `src/utils/save.js` et ajouter la migration.

## Rattrapage des simulés sans figer la page

Après une absence, le marché et les simulés rejouent le temps écoulé (jusqu'à 7 jours, un pas par 10 minutes). Fait d'un seul coup cela bloquait la page environ 4 secondes ; c'est désormais fait **par tranches de 12 pas** (`CATCHUP_SLICE` dans `utils/market.js`, `tickMarket(m, now, { maxSteps })`), l'application enchaînant les tranches tant que le marché a du retard (`marketBehind`) : aucune pause de plus de ~0,15 s. Le résultat est strictement le même que d'un seul coup (testé dans `test-simmarket.js`). Mesuré aussi : sauvegarder les simulés avec le joueur ne coûte que ~2 ms (360 Ko), donc ils restent dans la même sauvegarde.

## Profils des joueurs simulés

Chaque simulé a un **profil**, fixé une fois pour toutes d'après son identifiant (`traitsOf` dans `sim/lives.js`) : **occasionnel** (60 %), **régulier** (30 %) ou **acharné** (10 %). L'occasionnel joue peu et pas tous les jours (zèle ×0,7, séances ×0,6, jours de jeu ×0,8) ; le régulier est le comportement de base ; l'acharné joue de longues séances presque tous les jours, à fond (zèle environ 1,4 à 1,6, séances +3 h, 93 % des jours). Les acharnés ont un **objectif** : **xp** (85 % de combats, donjon deux fois plus souvent) ou **métiers** (récolte, raffinage et fabrication : peu de combats). Les parts d'activité des autres viennent toujours de leur type (combattant, récolteur…). À 30 jours depuis zéro (`node scripts/audit-global.js fresh 30`, qui donne un tableau par profil) : niveau médian d'environ 14 pour les occasionnels, 27 pour les réguliers et 34 pour les acharnés « xp » ; les acharnés « métiers » ont un métier médian d'environ 44 contre 13 pour les réguliers. Aucun profil n'est affiché au joueur : on le voit à leurs actes.

Les simulés riches (4 000 or et plus, en gardant 1 500 de réserve) **s'équipent aussi à l'hôtel des ventes** (`simBuysGear` dans `utils/market.js`) : ils achètent, à toi ou aux autres simulés, une pièce des paliers de leur classe qui vaut mieux que celle qu'ils portent, ce qui te donne des acheteurs pour ton équipement. Au-delà de 10 000 or, ils acceptent de payer leurs ingrédients jusqu'à 2,2 fois le cours (au lieu de 1,6). Effet mesuré sur l'or des acharnés : très faible, car ceux du plus haut palier n'ont plus de pièce à acheter.

À savoir : l'or des acharnés est élevé (une dizaine de fois celui d'un régulier), parce que la dernière région s'arrête au niveau 20 et qu'ils y restent en attendant la suite du jeu.

## Joueurs simulés (désactivés)

Pour les remettre : `SIM_PLAYERS = true` dans `src/sim/config.js`. Pour qu'ils répondent avec un modèle de langage : ajouter `ANTHROPIC_API_KEY` dans les variables d'environnement de Vercel (voir `.env.example` et `api/chat.js`), puis fixer une limite de dépense dans la console Anthropic. Sans clé, ils utilisent des phrases préécrites.

## Avantages des métiers

Tous les métiers montent jusqu'au **niveau 100** (30 xp × niveau pour passer au suivant, environ 148 500 xp au total). Chaque niveau apporte un peu plus, affiché dans l'Atelier avec la valeur du niveau suivant ; les premiers niveaux comptent plus que les derniers. Maximums au niveau 100 : **Récolte** (bûcheron, mineur, herboriste) récolte de 5 s au niveau 1 à 1 s au niveau 100 (`HARVEST_MS` dans `src/components/map/mapConstants.js`), 50 % de chance de récolte double, 20 % de chance de trouvaille d'une ressource peu commune (chêne, cuivre, sauge) ; **Raffinage** 40 % de chance de produire 1 unité de plus sans consommer plus ; **Fabrication** 30 % de chance de chef-d'œuvre (objet aux stats +10 %, vendu 25 % plus cher). Valeurs et courbe dans `src/utils/perks.js`, vérifiées par `test-perks.js`. Le **raffinage** rapporte 8 xp par unité de niveau 1 et 24 xp par unité de niveau 3 (`src/data/refining.js`) : le niveau 12, le plus haut requis par les recettes, demande une centaine d'unités. Le contenu actuel (recettes et ressources jusqu'au niveau 3) ne remplit pas 100 niveaux : les prochaines régions apporteront des ressources et recettes de niveaux plus élevés, qui donneront plus d'xp.

## Sorts : rangs et barre de combat

Chaque classe a **10 sorts** (niveaux 1, 3, 5, 7, 9, 12, 18, 26, 34, 42, dans `src/data/classes.js`), mais la barre de combat est limitée : le **sort de l'arme** (toujours là) + **3 sorts de classe** au départ, 4 au niveau 10, 5 au niveau 25. On choisit donc ses sorts, dans le panneau « Sorts » de l'onglet Personnage (clic sur un emplacement, puis « Placer »).

Chaque niveau donne **1 point de sort**. Un sort monte du rang 1 au rang 5 : passer du rang r au rang r+1 coûte r points (10 points pour un sort au maximum), donc on ne peut pas tout monter (49 points au niveau 50). Chaque rang renforce le sort (+8 % de dégâts, poison, affaiblissements, parade…) et le rang 5 réduit son coût de 1 PA. « Réinitialiser » rend les points contre de l'or (50 × niveau). Tout est dans `src/utils/spellbook.js`, vérifié par `test-spellbook.js`. Sauvegarde : `player.spellbook = { ranks, loadout }` (absent des anciennes sauvegardes : valeurs par défaut, rien à migrer). Les sorts au-delà du niveau 12 sont des premières valeurs, à équilibrer avec les monstres des prochaines régions.

## Les trois régions (niveaux 1 à 20)

Zone 1 est découpée en trois cartes de difficulté croissante, chacune avec ses monstres, son butin et sa propre ambiance visuelle (`theme` dans `src/data/maps.js`) : **Prairies Sauvages** (niveaux 1 à 8), **Champs Calcinés** (8 à 14, squelettes de fermiers, corbeaux, épouvantails et leur mini-boss l'Épouvantail Ancestral) et **Lisière des Ombres** (14 à 20, loups-garous, esprits errants, chevaliers déchus ; son mini-boss est le Veilleur Corrompu, voir plus bas). Les ennemis sont dans `src/data/zones.js`, les groupes dans `src/data/encounters.js`.

**Les mini-boss et la Dame en Deuil ont 8 PA** (les autres monstres 6, comme un héros, `ENEMY_PA` dans le moteur) : un groupe de trois héros dispose de 18 PA par tour, un boss à 6 PA agissait trop peu. La version difficile de la Dame garde les 8 PA (elle a déjà plus de vie, de dégâts, un sort de plus et une seconde phase plus brutale). Effet mesuré avec `simulate-zones.js` : seul, les mini-boss deviennent nettement plus durs (l'Épouvantail Ancestral au niveau conseillé : environ 70 % → 15 à 60 % selon la classe) ; en groupe ils restent gagnés presque à tous les coups, car le groupe les tue en quelques tours.

`node scripts/simulate-zones.js 100 squelettes,garous` fait jouer un joueur automatique de chaque classe contre les rencontres, à plusieurs niveaux (le niveau conseillé et trois niveaux plus bas), et affiche le taux de victoire et les PV restants. Objectifs : un groupe ordinaire gagné ≥ 85 % avec 35 à 70 % des PV restants au niveau conseillé, un mini-boss gagné 50 à 80 %, et trop dur trois niveaux plus bas. La simulation équipe le joueur de son palier d'équipement (palier 1 jusqu'au niveau 9, palier 2 de 10 à 15, palier 3 à partir de 16), sans la cape, les amulettes ni l'anneau : ces objets sont donc une marge de sécurité en plus.

## Équipement par paliers

Chaque région a son équipement, fabriqué avec ses drops (`src/data/gearTiers.js`). **Palier 1** (Prairies) : Vétéran, Apprenti, Traqueur. **Palier 2** (Champs Calcinés) : Plates du Fossoyeur (guerrier), Plumage du Charognard (assassin), Atours du Brasier (magicien). **Palier 3** (Lisière) : Harnois du Chevalier Déchu, Pelage du Loup-Garou, Mante de l'Esprit Errant. Chaque set a 5 pièces, une arme de la classe (et un bouclier pour le guerrier) ; les stats valent environ ×1,35 (palier 2) et ×1,9 (palier 3) celles du palier 1. Les nouveaux bonus de 5 pièces : riposte plus forte et épines (renvoi de 20 % des dégâts en feu noir), vol de vie, sorts qui ignorent une part de la défense (voir `src/combat/engine.js`).

Les trophées des boss donnent des objets communs à toutes les classes, fabriqués par le **Bijoutier** (nouveau métier : anneau du Cavalier Déchu, amulette de l'Armure Maudite, amulette du Cœur de Braise) et le Tailleur (cape de l'Épouvantail Ancestral). Un set de palier supérieur demande un niveau de métier plus élevé (+3 au palier 2, +6 au palier 3, voir `professions.js`). Les emplacements de reliques restent vides pour l'instant, réservés aux futurs boss. `test-gear.js` vérifie les paliers (stats croissantes, métiers, effets de combat).

## Le Veilleur Corrompu (boss de la Lisière)

Tout au bout de la carte de la Lisière des Ombres, dans le coin est. Il réapparaît au même rythme que les autres groupes (un groupe peut avoir son propre `respawnMs` dans `maps.js`, mais le Veilleur n'en a pas). Trois temps de combat :
- **Garde** : frappes lourdes qui brisent l'armure (Frappe écrase-garde) et **Regard du néant**, qui retire 2 PA au prochain tour du héros.
- **Appel**, sous 66 % de vie : il fait venir **2 esprits errants** (nouvelle mécanique `summon` des phases, dans `engine.js`). Ils entrent dans l'ordre de jeu juste après lui, ne rapportent ni xp, ni or, ni butin, et on ne dépasse jamais 3 ennemis.
- **Rage**, sous 33 % : +40 % d'attaque, et il débloque Feu noir et Souffle putride (actions avec `needsPhase`).

Butin : l'**Essence du Veilleur** (60 %, 1 à 2) et, à **5 %** seulement, une **arme unique propre à ta classe**. Il n'y a qu'un seul tirage : l'objet qui tombe est celui de la classe du joueur (`forClass` dans les drops de `zones.js`), donc chaque classe a exactement la même chance. Le boss ne lâche pas la clé du donjon : elle se fabrique (voir « Le Bricoleur »).
- **Lame du Veilleur** (guerrier, épée à une main) : ATK 46, DEF, PV, et « Dernier souffle » : une fois par combat, un coup mortel laisse 35 % des PV.
- **Croc du Veilleur** (assassin, dague) : ATK 40, 10 % critique, 6 % esquive, et 7 % des dégâts infligés rendus en PV.
- **Sceptre du Veilleur** (magicien, bâton à deux mains) : ATK magique 38, DEF magique, PV, et les sorts ignorent 25 % de la défense.

Ces armes sont légendaires, non fabricables, et gardent le type d'arme de leur classe (donc ses sorts). Leur `passive` est lu par `calcStats().passives` puis par le moteur de combat, avec les mêmes drapeaux que les bonus de set. L'emplacement de relique reste vide, pour un futur boss.

**Chaîne de quêtes** au tableau d'Aldenmoor (`CHAIN_QUESTS` dans `quests.js`, à partir du niveau 14, dans l'ordre, une seule fois) : faire taire 8 esprits errants, mettre 6 chevaliers déchus au repos, puis vaincre le Veilleur. Elles paient or, xp et réputation, jamais l'arme unique. `test-boss.js` vérifie le boss, l'appel, la rage, les armes uniques et la chaîne.

## Le Manoir Englouti (donjon, niveaux 20 à 26)

Un donjon de **4 salles pour un groupe de 3** (`src/data/dungeons.js`, logique dans `src/utils/dungeon.js`, écran `components/combat/DungeonRun.jsx`). L'entrée est un bâtiment sur la carte de la Lisière des Ombres, juste avant le Veilleur : elle ouvre la fiche du donjon (salles, butin possible, groupe). On n'y entre **qu'en groupe** (toi et deux compagnons) et avec une **Clé du Manoir Englouti** (voir « Le Bricoleur »), **consommée à l'entrée, même en cas de défaite**. Salles : le Hall inondé (2 serviteurs spectraux, un molosse), la Salle à manger (molosse, garde noyé, pleureuse), la Galerie des portraits (2 gardes noyés, une pleureuse), puis la Chapelle ardente : **La Dame en Deuil** et deux pleureuses.

- **Pas de soin entre les salles** : les PV sont reportés (`carry` dans `createCombat`). Un héros tombé dans une salle se relève avec 20 % de ses PV max (`DUNGEON_REVIVE`). Si le joueur tombe, l'expédition s'arrête : le butin des salles déjà gagnées reste acquis, la clé est perdue.
- **La Dame en Deuil** (5 000 PV) : phase 1, magie et Givre (affaiblissement, perte de PA) ; sous 50 % de vie, le rituel s'emballe (+25 % d'attaque, Feu, Poison, Givre, perte de 2 PA).
- **Butin exclusif** : Soie funéraire, Cuir de molosse et Plaque noyée (communes), Larme de deuil (peu commune), Essence de deuil (rare, la Dame). Elles sont marquées `dungeon` : le colporteur ne les vend jamais, elles ne viennent que du donjon (donc des joueurs).
- **Palier 4**, un set par classe, fabricable avec ce butin : **Armure du Garde Noyé** (guerrier, avec épée et bouclier), **Cuir du Veneur** (assassin, dague) et **Atours de la Veuve** (magicien, bâton). Environ ×1,4 le palier 3, métier niveau +9 (`TIER_LEVEL_OFFSET[4]`) ; l'essence de deuil n'est demandée que pour le plastron.
- **Relique universelle : Médaillon de la Dame en Deuil** (classes toutes confondues, emplacement relique) : **+1 PA définitif (7 PA au lieu de 6) et +10 % de dommages finaux** (physiques comme magiques). Elle tombe sur la Dame à **0,5 % exactement** : le drop est `fixed`, donc ni la Chance ni le bonus de butin de groupe ne le changent. Le passif est lu par `calcStats` (`paMax`) et par le moteur (`paMax`, `flags.finalDamage`).
- Équilibrage : `node scripts/simulate-dungeon.js [niveau] [palier] [essais]` fait jouer les trois classes en groupe. Avec le combat automatique (naïf, sans parade ni soutien), un groupe de niveau 24 en palier 3 finit environ 1 fois sur 10, en palier 4 environ 6 fois sur 10 : un joueur qui joue bien fera mieux que le bot. `test-dungeon.js` vérifie le moteur, les données, le taux de la relique et l'entrée sur la carte.

## Le Bricoleur (clés des donjons)

Nouveau métier de fabrication : il ne fait que les **clés de donjon**. Pour l'instant une seule, la **Clé du Manoir Englouti** (accessible dès le niveau 1 du métier, pour qu'on puisse y gagner de l'xp) : 3 Essences du Veilleur, 6 lingots de fer, 3 lingots de cuivre, 5 ectoplasmes et 500 or. La clé est un objet de type `cle` : elle reste dans le sac et ne s'équipe pas (`equipItem` ignore tout objet sans emplacement). Avantage du métier : jusqu'à 50 % de chance (au niveau 100) de ne consommer aucune ressource en fabriquant (l'or est dépensé quand même ; pas de chef-d'œuvre pour les clés). Les clés des prochains donjons s'ajouteront à `recipes.js`, avec un objet `type: "cle"`.

## Entre les salles du donjon : arrivée et potions

À chaque salle, le groupe **arrive d'abord dans la salle** (`components/combat/RoomScene.jsx`) : décor peint de la salle (`public/assets/dungeons/<donjon>/<salle>.webp`, champ `bg` dans `data/dungeons.js`, repris comme décor du combat), ton groupe à gauche, le **groupe de monstres de la salle** à droite, les PV de chacun. On y boit des **potions à volonté** (`utils/potions.js`) : aucune limite de nombre ni de coût, la potion est simplement retirée du sac. Une potion de soin rend une part des PV max à un héros vivant et blessé, l'élixir de rappel relève un héros tombé à 40 % (sans lui, un tombé se relève à 20 % à la salle suivante). Puis « Lancer le combat ». Pas de potion pendant le combat. Le groupe de compagnons est formé une fois pour toute l'expédition.

## L'Alchimiste (potions de soin)

Un métier de plus à l'atelier (`src/data/alchemy.js`, logique `canBrew` / `applyBrew` / `maxBrew` dans `utils/crafting.js`). Il distille des **potions**, des ressources empilables (elles se rangent au sac et au coffre, se vendent et s'achètent au marché, mais le colporteur n'en vend jamais : seuls les joueurs en produisent). Chaque potion coûte des herbes de la récolte (ortie, sauge) et, plus haut, des trophées de la Lisière : jamais de ressource de donjon.

| Potion | Niveau | Effet prévu | Ingrédients | Or |
|---|---|---|---|---|
| Potion de soin mineure | 1 | 25 % des PV | 3 orties | 6 |
| Potion de soin | 8 | 50 % des PV | 2 orties, 2 sauges | 25 |
| Grande potion de soin | 16 | 80 % des PV | 4 sauges, 2 ectoplasmes, 1 voile spectral | 80 |
| Élixir de rappel | 24 | relève un héros tombé à 40 % | 5 sauges, 2 voiles spectraux, 1 pelage maudit | 200 |

Avantage du métier : jusqu'à **40 %** de chance de distiller une potion de plus (comme le raffinage, sans rien consommer de plus). Elles servent **entre les salles du donjon** (voir « Entre les salles du donjon »).

**Les simulés et les potions** (`src/sim/lifePotions.js`). Un simulé que le donjon intéresse (niveau 20 passé, et une clé, une expédition déjà faite ou de l'essence du Veilleur) distille ses propres potions à l'atelier avec les mêmes règles que toi, pour emporter 3 potions de soin, 2 grandes potions et 1 élixir. Tant que son niveau d'Alchimiste ne permet pas la potion visée, il s'entraîne sur la meilleure qu'il sait faire ; les herbes viennent de sa récolte, de l'hôtel des ventes (ses achats sont dans la liste de courses du marché) ou du marchand de secours. Ses potions en trop (au-delà de 8) sont mises en vente à l'hôtel des ventes : tu peux les lui acheter. En expédition, il emporte le contenu de son sac, boit entre les salles comme un joueur (`autoDrink` : le plus blessé d'abord, la plus petite potion qui suffit, l'élixir pour un tombé) et ses chances sont estimées avec ce sac (`dungeonOdds`) ; les potions bues sortent de son sac.

**Équilibrage du Manoir** (`node scripts/simulate-dungeon.js niveau palier essais potions`, groupe de trois bots naïfs, équipement du palier) : sans potion, le donjon est très dur (≈ 8 % de victoires au palier 3, ≈ 62 % au palier 4 au niveau 24). Avec un petit sac (2 potions de soin + 1 grande, à peu près 230 or) : ≈ 65 % au palier 3 (niveau 22–24) et ≈ 96 % au palier 4 ; avec un sac plein presque 100 %. Les morts se jouent surtout contre la Dame en Deuil. J'ai donc **laissé les ennemis tels quels** : les potions sont désormais la condition d'entrée, et l'équipement du palier 4 récompense la préparation.

## Amélioration de l'équipement
Chaque pièce portée (ni relique, ni clé) peut passer **+1, +2, +3** à l'atelier de n'importe quelle ville : **+10 % de stats par niveau** (sauf la chance de butin et la vitesse), sans risque d'échec, et le niveau reste écrit sur la pièce (`plus`). Un niveau coûte (`data/upgrade.js`, logique dans `utils/upgrade.js`) :
- des **éclats** : *brut* (monstres de zone) pour +1 (×3), *dense* (mini-boss) pour +2 (×1), *pur* (donjon) pour +3 (×2) ;
- la **ressource rare de la classe**, trouvée en plus en récoltant (6 % au niveau 1 du métier, 20 % au niveau 100) : guerrier = Veine d'acier (mineur), magicien = Pétale d'âme (herboriste), assassin = Sève d'ambre (bûcheron) ; 1, 2 puis 3 unités ;
- de l'**or** : valeur de la pièce × 3, × 8 puis × 20, plus la taxe de la ville (1 % ici, inscrite dans `taxPaid`).
Une pièce améliorée se revend plus cher (+50 % de sa valeur par niveau). C'est le grand puits d'or : un +3 sur tout l'équipement coûte bien plus que la fabrication du set.

**Simulés** (`sim/lifeUpgrade.js`) : ils récoltent la ressource rare si leur métier est le bon, ramassent les éclats en combat, et achètent ce qui manque à l'hôtel des ventes (seulement s'ils ont l'or). À l'atelier ils montent d'abord toutes leurs pièces à +1 (arme, plastron…), puis +2, puis +3 ; une pièce qu'ils remplacent garde son +N dans un petit stock (`plusStock`, 4 au plus) et ils la mettent en vente à l'hôtel des ventes avec son niveau, plus chère ; un simulé peut aussi l'acheter déjà améliorée. Leurs chances de victoire en tiennent compte (`plusBucket`). `node scripts/audit-global.js` affiche le nombre d'améliorations et l'or dépensé par profil.

## Le Manoir Englouti difficile
Même manoir (mêmes salles, décors et visuels), choisi par le bouton **Difficile** de la fiche d'entrée. Les monstres (`<clé>_difficile`, générés dans `data/zones.js` à partir des normaux avec `HARD_MULT`) ont 70 % de PV, 50 % d'attaque et 25 % de défense en plus, et rapportent 60 % d'xp et 50 % d'or de plus ; la Dame en Deuil gagne un sort (Requiem funèbre) et une seconde phase à +40 %. Niveau conseillé : 26 et plus.
- **Clé** (`cle_du_manoir_difficile`, Bricoleur niveau 5) : 2 essences de deuil (le rare du boss du donjon normal), 6 larmes de deuil, 12 lingots de fer, 6 de cuivre, 10 ectoplasmes, plus la taxe de la ville.
- **Éclats purs** : 3 à 5 garantis sur le boss, 25 % sur chaque autre monstre (10 % au normal).
- **Médaillon du Veuvage éternel** : 0,3 % exactement sur le boss. +1 PA, +15 % de dommages finaux, 4 % de vol de vie et +10 % de butin ; il prend l'emplacement de relique (un seul), donc on peut posséder les deux Médaillons mais en porter un seul. Le Médaillon de base ne tombe que dans le donjon normal, l'éternel que dans le difficile.
Simulés (`sim/lifeDungeon.js`, état `life.djh`) : ils visent la clé difficile après un premier donjon normal réussi et à partir du niveau 26, avec l'essence de deuil gagnée par eux ; ils tentent d'abord la difficile (si leurs chances mesurées dépassent 30 %), sinon la normale. Les deux donjons partagent le repos de deux jours.

## Emplacements de récolte
Sur chaque carte de région, les nœuds sont regroupés **par métier en trois coins** (`data/maps.js`) : la forêt (frênes et chênes) pour le bûcheron, la mine (filons de fer et de cuivre) pour le mineur, le champ d'herbes (orties et sauge) pour l'herboriste. Chaque coin tient dans environ 6 tuiles autour de son centre, loin des groupes de monstres, de l'arrivée et des deux autres coins, et choisi près du décor qui lui va (arbres, rochers, étangs). Une tuile libre sépare toujours deux nœuds, et aucun nœud ne ferme un passage. Les trois régions ont été agrandies d'environ 50 % (59×37, 63×39, 63×39 tuiles) : 18 groupes de monstres et 44 à 45 nœuds chacune (9 frênes, 6 chênes, 8 filons de fer, 5 de cuivre, 10 orties, 6 sauges). Une ancienne sauvegarde dont la position tombe dans un obstacle de la nouvelle carte repart de l'arrivée. `scripts/test-nodes.js` vérifie tout ça.

## Taxe de fabrication des villes

Fabriquer, raffiner et distiller n'ont plus de coût fixe : on paie une **taxe de la ville** (`utils/cityTax.js`), un pourcentage du **prix de ce qu'on obtient** (pour un objet : ses ingrédients plus sa main-d'œuvre, `itemValue` ; pour une matière raffinée ou une potion : sa valeur ; au moins 1 or). **1 % par défaut**, réglable plus tard de **0 % à 5 %** par la guilde qui contrôlera la ville. L'or des recettes (`gold`) reste dans les données comme main-d'œuvre : il compte dans le prix de l'objet et donne l'xp du métier, mais n'est plus dépensé.

Chaque grande région dépend d'une ville (`data/cities.js` ; aujourd'hui une seule : Aldenmoor, qui couvre la ville, les Prairies Sauvages, les Champs Calcinés et la Lisière). Où que tu sois dans la grande région, le raccourci « Atelier » ouvre l'atelier de **ta** ville, avec sa taxe (affichée en haut de l'atelier, et sur chaque recette). La guilde viendra écrire le taux dans `world.cities[ville].taxRate` (toujours borné à 0–5 %, `cityTaxRate`) ; en attendant, `player.taxPaid[ville]` tient le registre de ce que tu as payé, c'est ce que la guilde percevra. Les simulés paient la taxe par défaut mais leur registre n'est pas tenu.

À savoir : à 1 %, l'or dépensé en fabrication tombe à quelques pièces (une clé de donjon passe de 500 or à 16) : l'or n'est presque plus un puits à l'atelier. Sur 30 jours simulés, l'or médian des simulés passe d'environ 1 200 à 2 900. C'est la taxe réglable (jusqu'à 5 %) qui rééquilibrera cela.

## Raffinage

Entre la récolte et la fabrication, il y a le raffinage, à l'atelier : quatre métiers (fondeur, scieur, tanneur, tisserand), chacun avec son niveau. Deux matières brutes donnent une matière raffinée (lingot, planche, cuir, étoffe, fil), qui vaut un peu plus que les deux brutes, en échange d'un peu d'or et de temps. Les recettes d'équipement demandent maintenant ces matières raffinées. Les ressources raffinées se vendent à l'hôtel des ventes (les joueurs simulés en proposent) et certaines quêtes de livraison les demandent. Données dans `src/data/refining.js` ; `node scripts/simulate-economy.js` affiche le bénéfice de chaque transformation.

## Quêtes et réputation

Le tableau de quêtes d'Aldenmoor (bâtiment de la ville) propose chaque jour une sélection de quêtes : vaincre des monstres, récolter, rapporter des ressources (retirées du sac à la remise, on peut donc les acheter à l'hôtel des ventes) ou fabriquer un objet. On en garde 3 en cours, le Journal les suit. Seuls les combats, récoltes et fabrications faits après l'acceptation comptent (compteurs dans `src/utils/counters.js`). Chaque quête donne or, xp et réputation à la ville : chaque niveau de réputation ajoute +3 % d'or aux quêtes, et tous les 2 niveaux +5 emplacements au coffre. Les modèles sont dans `src/data/quests.js`, la logique dans `src/utils/quests.js`. Règle testée : une quête ne paie jamais plus de 1,25 × la valeur du travail demandé (marché ou monstres).

## Vision du monde (à construire plus tard)

- **Villes revendiquables.** Chaque grande région aura sa grande ville et son hôtel des ventes, comme dans New World. Une guilde peut revendiquer la ville et contrôler le territoire. Elle fixe la taxe de mise en vente de la ville, de 1 % à 30 %, et cette taxe va dans le coffre de guilde géré par le chef. Une ville sans guilde garde la taxe par défaut de 10 % (`TAX_RATE` dans `src/utils/market.js`). Acheter reste toujours sans taxe. Cela demandera un marché et un taux par ville.
- **Ressources uniques par région.** Chaque grande région a des ressources introuvables ailleurs (par exemple le minerai d'or, nom à éviter pour ne pas confondre avec la monnaie, uniquement en région 3). On les réserve aux recettes de haut niveau de la région, pour ne jamais bloquer un joueur, et il faudra décider comment elles circulent entre villes (transport, bots marchands). Les bots posteront alors leurs annonces selon la région où la ressource existe.

## Idées à venir

**Groupes de 3 (en cours)** : depuis la fenêtre d'engagement sur la carte, **« En groupe »** emmène deux alliés bots (les deux autres classes, au niveau du joueur, avec l'équipement de leur palier : `src/sim/partyBots.js`). Le moteur gère plusieurs héros (`allies` dans `createCombat`, ids `ally0` / `ally1`) : ils entrent dans l'ordre d'initiative, jouent seuls (le sort le plus rentable sur l'ennemi le plus faible, sans parade ni soutien), et les ennemis visent un héros vivant au hasard. Seul le joueur compte pour la défaite (sa mort perd le combat) et pour le butin : xp et or sont ceux d'un combat solo, les renforts du Veilleur ne rapportent rien. Les ennemis ne sont **pas** renforcés en groupe (`PARTY_HP_SCALE` vaut 1 partout) : à trois, le combat est plus facile et plus court. En contrepartie le **butin est meilleur** : la chance de chaque drop est multipliée par 1,25 à 2 héros et 1,5 à 3 (`PARTY_DROP_MULT` dans `engine.js`), armes uniques comprises, et s'ajoute au bonus de butin de l'équipement. En échange, le **solo rapporte +25 % d'xp** (`SOLO_XP_MULT`). Seul le bonus de butin du joueur compte : celui des équipements des bots n'est pas cumulé. `test-party.js` vérifie tout ça.

**Groupe** (permanent, comme dans Dofus) : l'onglet « Groupe » (`GroupPanel.jsx`, logique dans `src/utils/group.js`) permet d'inviter jusqu'à 2 joueurs simulés **connectés** (ceux qui jouent à cet instant selon leurs horaires, `isActive`) — ceux de ta guilde d'abord, puis les plus proches de ton niveau (écart maximal de 10 niveaux). Le groupe reste formé entre les combats (`player.companions`, sauvegardé) ; un membre qui se déconnecte en sort tout seul (`cleanGroupAction`, vérifié toutes les 10 s). Un rappel du groupe (`GroupBadge.jsx`, avatars, pseudos et niveaux) s'affiche en bas à gauche de la carte et mène à l'onglet. « En groupe » sur la carte emmène les membres présents (pas de complément générique, `buildAllies(..., { fill: false })`), les donjons complètent avec des alliés génériques. Après une victoire, **chaque membre gagne son propre xp, son or et son butin** (`creditGroup` → `groupFightStep` dans `sim/lives.js`, bonus de butin ×1,25 à deux et ×1,5 à trois) ; rien n'est retiré des gains du joueur. Un simulé n'accepte pas toujours l'invitation (`acceptsInvite` : probabilité selon son profil — occasionnel 70 %, régulier 80 %, acharné de l'xp 90 %, acharné des métiers 40 %, +10 points pour ceux de ta guilde — tirée une fois par pas de 10 minutes, donc insister ne sert à rien) ; un membre qui se déconnecte quitte le groupe et un message le dit. Pendant qu'un simulé est dans ton groupe, **sa vie simulée est en pause** (`sims.busy[id]`, renouvelé toutes les 10 s par `cleanGroupAction`, ignoré par `stepLivesOne`) : il ne gagne qu'avec toi, et sa vie reprend dès qu'il quitte le groupe ou si tu fermes le jeu. **Plus d'allié générique** : ni sur la carte ni dans les donjons, seuls les vrais joueurs connectés du groupe t'accompagnent (on peut entrer seul dans un donjon, mais il est pensé pour trois). Les sims améliorent leurs pièces (`plusBucket`), et cela compte dans le combat.

**Aventuriers sur les cartes** : sur les cartes de région, 3 petits groupes de 1 à 3 simulés (niveau de la région, niveaux proches entre eux) se promènent ensemble, vont affronter un groupe de monstres ordinaire (jamais un mini-boss, jamais celui que tu engages) et le vainquent après une dizaine de secondes : le groupe est alors vraiment éliminé et réapparaît après son délai habituel, comme si tu l'avais tué. Un groupe en cours de combat est assombri (⚔) et ne peut pas être engagé. Au plus une victoire toutes les 14 à 30 secondes sur une carte, pour qu'ils ne la vident pas. Logique pure dans `src/sim/mapLife.js` (testée par `test-maplife.js`), rendu partagé avec la ville (`CityCrowd`), interrupteur `SIM_ON_MAPS` dans `sim/config.js`.

**Vie des simulés (personnages persistants)** : chaque aventurier simulé a son propre personnage (niveau, xp, or, métier de récolte), rangé dans la sauvegarde du joueur avec son marché (`player.market.sims`) et rejoué avec le temps réel (`src/sim/lives.js`, `simWorld.js`). Tout est calculé à partir de l'heure seulement, par pas de 10 minutes (au plus 7 jours rattrapés à l'ouverture) : même heure, même histoire, et rejouer en un bloc ou en plusieurs donne le même résultat. Chacun a ses horaires (quelques heures par séance, surtout le soir, certains jours sans jouer), son zèle et son métier ; selon son activité il combat (xp, or) ou récolte (xp de métier). Il garde dans son **sac** ce qu'il ramasse : les ressources des drops de monstres et de sa récolte, et l'équipement qui tombe (celui de sa classe seulement, comme pour toi ; au-delà de 24 pièces il revend la plus ancienne pour de l'or). Il porte de l'équipement (`gear`), **raffine et fabrique** les pièces de son palier avec les mêmes règles que toi (`applyRefine` / `applyCraft` : niveau de métier, ressources, or, xp de métier ; `src/sim/lifeCraft.js`) : il vise le set de son palier de niveau, s'entraîne sur ce qu'il sait faire quand son métier est trop bas, porte toute pièce meilleure que la sienne et garde l'ancienne dans son sac. Ce qui lui manque, il l'achète à un marchand (130 % de la valeur, plus cher pour les ressources rares) ; au-delà de 40 unités d'une ressource il revend le surplus à 60 %. Les compagnons de groupe combattent avec cet équipement réel.

**L'hôtel des ventes, côté joueur** (`components/city/MarketPanel.jsx`, présentation dans `utils/marketBook.js`) : conçu comme celui de Dofus. Trois onglets. *Acheter* : catégories à gauche (ressources par origine, équipement par emplacement), liste au milieu avec le prix du lot de 1, 10 et 100 (le coût réel pris sur les offres les moins chères), recherche, fiche à droite avec le cours sur 24 h, le choix du lot et la liste des offres. *Vendre* : ton sac à gauche, à droite la quantité, le prix (bouton « marché » et « −1 or »), la taxe de 10 % et le net, et les offres concurrentes. *Mes ventes* : tes emplacements, occupés, libres ou verrouillés avec le niveau qui les ouvre. **Emplacements de vente** : 3 au niveau 1, un de plus tous les 5 niveaux, 12 au maximum (niveau 45) ; une annonce occupe un emplacement quelle que soit la quantité (`listingSlots` dans `utils/market.js`). `test-marketbook.js` et `test-market.js` vérifient le catalogue, les lots et les emplacements.

**Les simulés sur l'hôtel des ventes** (`SIM_MARKET` dans `sim/config.js`, `enableSimMarket` dans `utils/market.js`) : le monde des simulés et le marché avancent ensemble, pas par pas de 10 minutes. Les annonces des « bots » sont celles de vrais simulés qui mettent en vente ce qu'ils ont en trop dans leur sac (ils paient la taxe de mise en vente et touchent l'or de la vente ; une annonce expirée retourne dans leur sac), ils y achètent les ingrédients qui leur manquent pour fabriquer (jamais au-delà de 1,6 fois le cours) et, quand tu leur achètes quelque chose, l'or leur est versé au pas suivant. Un Colporteur d'Aldenmoor comble les pénuries de ressources courantes et peu courantes pour que le marché ne soit jamais vide (jamais de ressource rare, ni d'équipement au-dessus du commun : reliques, épiques et pièces fabriquées ne viennent que des joueurs) (prix un peu au-dessus du cours). Désactivé (`false`), c'est l'ancien marché abstrait. Mesuré sur 30 jours : prix médian ≈ 1,2 fois la valeur de base (1,0 avec l'ancien marché), environ 3/4 des annonces viennent encore du colporteur, le reste de simulés. Au-delà du niveau de la dernière région l'xp est divisée par 2 tous les 2 niveaux, faute de contenu plus difficile. Leurs niveaux du moment sont ceux affichés partout (compagnons, cartes, ville). `node scripts/simulate-lives.js fresh 60` montre les courbes de progression ; `test-lives.js` vérifie le tout.

**Fresh start du lancement** : dans `src/sim/config.js`, `SIM_START = { mode: "generated", epoch: 1 }` pendant les tests (ils démarrent au niveau tiré par la population). Pour le lancement, passer à `{ mode: "fresh", epoch: <Date.now() du jour J> }` : tout le monde repart au niveau 1 à cet instant, et les sauvegardes de simulés du navigateur sont effacées automatiquement (elles ne correspondent plus au départ).


**Quêtes des simulés** (`sim/lifeQuests.js`) : chaque simulé a un carnet `life.quests` de la même forme que le tien (quêtes actives, faites du jour, réputation d'Aldenmoor, chaîne de quêtes, compteurs d'activité). Pendant ses séances il passe au tableau du jour (le même que le tien, via `boardFor`), accepte jusqu'à 3 quêtes qu'il peut réellement faire (chasse d'un ennemi de sa région, récolte, livraison s'il a déjà les ressources dans son sac ; pas de fabrication pour l'instant ; les mini-boss s'ajoutent à leurs cibles possibles quand ils ont le niveau), les rend avec les vraies fonctions `acceptQuest` / `completeQuest` (or, xp, réputation, bonus d'or de la réputation) et abandonne celles qui traînent plus de 2 jours. Ses victoires, récoltes et fabrications alimentent ses compteurs, et quand il a une quête de chasse il va en priorité vers les monstres demandés. Les anciennes sauvegardes reçoivent un carnet vide.

**Caractéristiques et grimoire des simulés** (`buildOf` dans `sim/partyBots.js`) : chacun a son style de jeu, tiré de son identifiant et donc stable : part de points dans la caractéristique principale (50 à 80 %), une caractéristique secondaire (chance, vitesse…), goût pour les sorts de zone, sorts montés haut ou répartis. Sa répartition est recalculée à partir de son niveau, comme si les points avaient été dépensés un par un ; les compagnons que tu emmènes combattent avec ce style.


**Coffre des simulés** (`sim/lifeBank.js`) : même coffre que le tien (`utils/bank.js` : 20 emplacements, agrandissements payants, emplacements offerts par la réputation d'Aldenmoor). Un simulé y range ses ressources en trop (au-delà de 30 unités il en garde 15 sur lui) et ses équipements de réserve (au-delà de 12 dans le sac) au lieu de les brader ; il en sort ce qui manque avant de fabriquer, avant d'aller acheter au marché et pour une quête de livraison, reprend une pièce rangée si elle vaut mieux que celle qu'il porte, et agrandit le coffre quand il est plein s'il a deux fois le prix. Le trop-plein d'une ressource rangée (au-delà de 150 unités) est mis en vente à l'hôtel des ventes avec le reste de leurs annonces, et au-delà de 400 unités le reste est bradé au marchand (60 %), pour que les stocks ne gonflent pas sans fin. Après un mois, ≈ 90 % des simulés ont un coffre bien rempli ; l'offre du marché reste du même ordre.

**Sac du joueur** (onglet 🎒 « Sac », `components/bag/BagPanel.jsx` ; règles dans `utils/bag.js`, testées par `scripts/test-bag.js`) : 40 emplacements au départ (le coffre en a 20) : un objet = 1 emplacement, un type de ressource = 1 emplacement (quelle que soit la quantité), l'équipement porté n'en prend pas. Huit agrandissements payants de +5 (150, 400, 900, 1 800, 3 200, 5 500, 9 000 et 15 000 or) montent à 80. Le sac plein ne bloque que ce qui demande un **nouvel** emplacement (on peut toujours ajouter à une pile déjà là) : le butin de combat qui ne tient pas est perdu (les équipements passent avant les nouveaux types de ressources, l'écran de victoire le dit), et la récolte (la trouvaille d'abord), la fabrication, le raffinage, les potions, les achats et reprises d'annonces au marché, les retraits du coffre et de la guilde, ou retirer une pièce équipée sont refusés (`bagGuard`). Une fabrication qui consomme entièrement une pile libère sa place. Le butin est géré dans `applyRewards`, les actions du joueur dans `hooks/usePlayer.js`. Un sac qui contient déjà plus que la capacité (ancienne sauvegarde, mode test) est agrandi sans frais de ce qu'il faut (`grandfatherBag`, appelé par `repairPlayer`) : on ne retire rien à un joueur. Les joueurs simulés ont déjà leur propre sac (voir ci-dessous) et ne sont pas concernés.


**Classement** (onglet 🏆, `components/ranking/RankingPanel.jsx`, logique dans `utils/ranking.js`) : les 500 simulés et toi dans une même liste, triée au clic par niveau, fortune (l'or porté), meilleur métier (ou un métier précis au choix) ou temps de jeu, avec recherche par nom et filtre de classe. Quatre cartes en haut donnent ton rang sur chaque critère ; ta ligne reste affichée en bas même hors du top 100. La liste se met à jour en direct avec le monde des simulés. Le temps de jeu d'un simulé compte les pas de 10 minutes où il joue (`life.played`) ; le tien (`player.playSec`) compte 30 s toutes les 30 s quand l'onglet est visible et que tu as bougé, cliqué ou tapé dans les 5 dernières minutes. Les parties créées avant n'ont pas d'historique : leur temps de jeu repart de 0. `test-ranking.js` vérifie les tris, les rangs et le temps de jeu des simulés.

**Guildes** (onglet 🏰 « Guilde », `components/guild/GuildPanel.jsx` ; règles dans `data/guild.js`, logique dans `utils/guildCore.js` (données), `utils/guildActions.js` (actions du joueur), `sim/guilds.js` (les simulés) et `utils/guildBonus.js` (bonus)) :
- **Règles** : 50 membres au maximum ; fonder coûte 10 000 or ; niveau de guilde 1 à 50, qui monte avec les **quêtes de guilde** (trois en cours : monstres vaincus, ressources récoltées, objets fabriqués, or donné ; tout ce que font les membres compte, l'objectif grandit avec le nombre de membres et le niveau ; une quête finie donne de l'xp de guilde et de l'or à la caisse). La **caisse** se remplit par les quêtes et les dons ; le chef s'en sert pour les paliers et les onglets du coffre.
- **Paliers de bonus** : 10 paliers, un tous les 5 niveaux de guilde, à débloquer dans l'ordre avec le niveau requis ET l'or de la caisse (de 3 000 à 400 000). Ils ajoutent, au total : +10 % d'xp de personnage, +15 % d'xp de métier, +10 % de butin, +15 % de rendement de récolte, +10 % de rendement de raffinage et d'alchimie (chance d'une unité de plus) et +5 % de chances de chef-d'œuvre en fabrication. Les bonus s'appliquent au joueur (`calcStats`, `rollRewards`, `applyGather`, `applyRefine`, `applyBrew`, `applyCraft`) et aux simulés (`life.gb`), avec les mêmes fonctions.
- **Coffre de guilde** : jusqu'à 6 onglets de 30 emplacements (un objet ou un type de ressource par emplacement) ; le premier est offert, les autres s'achètent avec la caisse selon le niveau de guilde (5, 10, 20, 30, 40). Tout membre y dépose et y retire ; un journal garde les derniers événements.
- **Rangs** : chef (un), bras droit (un), officiers, recrues. Tous déposent dans le coffre et donnent à la caisse ; **chef et bras droit** dépensent la caisse (paliers, onglets) et retirent du coffre. On peut exclure un rang strictement plus bas que le sien (à partir d'officier). Le chef nomme tous les rangs (nommer un bras droit remplace l'ancien, qui devient officier) et passe le commandement (il devient alors bras droit) ; le bras droit nomme les officiers. Si le chef part, le bras droit prend la suite (sinon le membre le plus actif) ; seul, la guilde disparaît et son coffre revient au joueur. Le chef simulé nomme son bras droit (guilde de 6 membres et plus) et un officier pour 8 membres, parmi les plus actifs, sans toucher au rang du joueur.
- **Blason** : à la création, comme dans Dofus, le joueur compose le blason de sa guilde (`data/emblems.js`, `components/guild/EmblemEditor.jsx` et `Emblem.jsx`) : 8 formes d'écu, 7 motifs, une palette de 16 couleurs (fond, motif et bord, symbole) et 30 symboles (23 silhouettes animaux, armes et objets générées avec Ludo dans `public/assets/emblems/`, teintées en CSS, plus 7 dessins vectoriels), avec aperçu en direct et bouton « Au hasard ». Le blason est rangé dans la guilde (`emblem`, numéros dans les listes) ; les guildes des simulés en reçoivent un tiré au sort. Pour ajouter un symbole : déposer un PNG noir à fond transparent dans `public/assets/emblems/` et l'ajouter à `SYMBOLS` (à la fin, pour ne pas décaler les blasons existants).
- **Recrutement** : le chef et le bras droit fixent un niveau minimum pour rejoindre (onglet Aperçu, `minLevel` dans la guilde, 0 = ouvert à tous). Il vaut pour le joueur (`joinGuildAction`, raison `niveau_requis`) comme pour les simulés (`sim/guilds.js`) ; ceux qui sont déjà membres restent.
- **Sentinelles** (étape 1 ; onglet « Sentinelles » de la guilde, `components/guild/Sentinels.jsx` et `SentinelSprite.jsx` ; chiffres dans `data/sentinel.js`, règles dans `utils/sentinel.js`, tests `scripts/test-sentinel.js`) : adaptation du percepteur de Dofus. Un golem de pierre (`public/assets/sentinel/golem.png`, fait avec Ludo) que la guilde pose dans une région (Prairies, Champs Calcinés, Lisière ; pas les donjons) : le dessin tient une hampe nue et la bannière est le blason de la guilde, posé par-dessus en HTML (pas de dessin à refaire par guilde). Une seule sentinelle par région (la première arrivée garde la place) ; la guilde en tient 1, puis une de plus tous les 10 niveaux ; la pose coûte de l'or de la caisse (2 000 / 5 000 / 10 000, selon la région) et se fait par le chef ou le bras droit. La sentinelle agit comme un aventurier invisible de plus dans **chaque** combat de sa région : elle a son propre tirage de butin (l'or et les ressources du monstre, `SENT_LOOT_SHARE` = la moitié d'un tirage de joueur, jamais d'équipement) et ne prend rien aux autres. Le butin arrive dans son stock, plafonné selon le niveau de la guilde (or : 1 000 + 400 × niveau ; par ressource : 50 + 10 × niveau) : le chef ou le bras droit la « relève » (l'or va à la caisse, les ressources au coffre, ce qui ne tient pas reste sur place) ; on ne peut la retirer qu'une fois le stock vide. Les combats du joueur la nourrissent (`creditPlayerFight`, appelé par `applyCombatRewards` ; la région se lit d'après les monstres tués), ceux des simulés aussi (`onFight` de `stepLife`) ; les guildes simulées en posent et les relèvent. L'annuaire `sims.guilds.sent` (région → guilde) est réparé toutes les heures par `rebuildSent` ; une guilde dissoute libère ses régions. **La sentinelle comme un personnage** (`data/sentinel.js` pour les chiffres et la liste des sorts, `utils/sentinelBuild.js` pour les règles, fiche dans `components/guild/SentinelSheet.jsx`, tests dans `test-sentinel.js`) : une seule fiche par guilde, pour toutes ses sentinelles (`g.sentBuild`). Chaque niveau de guilde donne 3 points à répartir (chef et bras droit) entre vitalité (PV), force (dégâts), défense, vitesse (initiative) et chance (butin) ; une caractéristique ne reçoit pas plus de 60 % du total. Ce qui compte, c'est la **part** de points dans le total possible (avec un plancher de 60 points, le total d'une guilde de niveau 20 : une jeune guilde a une sentinelle plus faible, et un point de plus au niveau 1 ajoute une quarantaine de PV, pas des centaines) : la sentinelle part d'un héros de référence du niveau de la guilde (guerrier de `partyBots.js`) et sans point elle a 1,5 fois ses PV et 30 % de son attaque et de sa défense ; à 20 % partout, 3,5 fois les PV et 70 % ; la chance fait passer sa part de butin de 0,3 à 0,72 tirage de joueur. Remise à zéro : 100 or par niveau, pris dans la caisse. Les sorts (3 équipés au plus) : un de départ puis un nouveau tous les 5 niveaux de guilde, cinq attaques (dont une de zone) et cinq soutiens (Peau de granit, Mousse vivante, Bouclier de roche, Carapace, Rempart) ; le meilleur sort est au niveau 50. Sans choix de la guilde, elle équipe ses 3 sorts les plus récents. Le moteur de combat sait pour cela lancer des soutiens sur soi, des attaques de zone et appliquer défense accrue (`armor`), régénération (`hot`), bouclier (`shield`) et réduction des dégâts (`reduce`) à un ennemi. Les guildes des simulés placent leurs points d'elles-mêmes (`autoAlloc`, une façon de jouer par guilde). L'équilibrage se regarde avec `node scripts/simulate-sentinel.js`.
 **Attaquer une sentinelle** (étape 2, première partie ; `utils/sentinelFight.js`, plaque `components/map/SentinelTag.jsx` sur la carte de la région, `simulate-sentinel.js` pour l'équilibrage) : sur la carte d'une région où une autre guilde a posé sa sentinelle, une plaque donne « Attaquer seul » ou « En groupe » (comme un combat normal, avec les 2 alliés bots). Le combat est un vrai combat au tour par tour contre un monstre fabriqué à la volée (`ENEMY_EXTRA` / `enemyDef` dans `data/zones.js`, donc hors bestiaire) : 70 % de l'attaque et de la défense d'un héros du niveau de la guilde, 3,5 fois ses PV, trois sorts de base (Poing de pierre, Jet de roche, Écrasement), et la bannière de la guilde sur la hampe. Les attaquants ont `SENT_ROUNDS` = 12 tours de table pour la tuer (`maxRounds` du moteur), sinon la défense gagne. **Victoire** : son stock (or et ressources) est partagé à parts égales entre le joueur et les simulés de son groupe (`winAttackAction(..., groupIds)`, le reste d'une division non entière revient au joueur) ; la part du joueur va dans le sac d'abord, puis dans son coffre personnel s'il est plein (ce qui ne tient nulle part est perdu), celle des simulés dans leur propre sac et leur or, dont ils font ensuite ce qu'ils veulent comme de vrais joueurs (vendre, garder, fabriquer) ; la sentinelle disparaît et la guilde pourra en reposer une (en repayant). **Défaite** : la sentinelle est intouchable pendant 1 h (`shield`). Seul, c'est dur ; à trois, une sentinelle sans défenseurs tombe presque toujours. **Les défenseurs** (`utils/sentinelDefense.js`) : jusqu'à `DEFENDERS_MAX` = 3 membres de la guilde qui sont **connectés** à ce moment-là (`isActive` des simulés, tirés dans un ordre stable pour l'heure en cours) combattent à côté de la sentinelle. Chacun devient un monstre de combat fabriqué à la volée avec ses vraies caractéristiques (classe, niveau, répartition de points, équipement porté et niveau moyen d'amélioration +0 à +3 de ses pièces, `plusOf`), ses sorts d'attaque (sans soutiens) et son apparence retournée vers les héros (`defender`, `flip` dans la définition). La sentinelle est toujours le premier ennemi : le moteur a un `objective: "sentinel"` (la victoire est acquise dès qu'elle tombe, même si ses défenseurs sont debout) et la défaite vient du temps (12 tours) ou de la mort du héros. La plaque de la carte annonce le nombre de défenseurs en ligne et leur niveau. Ils sont aussi forts que de vrais joueurs de leur niveau : à niveau égal, trois attaquants face à trois défenseurs gagnent environ une fois sur deux (`simulate-sentinel.js`, `evaluate(classe, niveau, groupe, n, plan, nbDéfenseurs)`). **Les attaques des simulés et la défense** (`sim/sentinelWar.js`, onglet `components/guild/Defense.jsx`, bandeau d'alerte dans `App.jsx`, tests `scripts/test-sentinelwar.js`) : chaque heure, une guilde simulée peut en attaquer une autre qui contient le joueur (`WAR_P` = 2 % par heure et par guilde, pas plus d'une attaque toutes les 8 h sur la même guilde, une seule à la fois) avec 1 à 3 de ses membres connectés dont le niveau convient à la région (un attaquant seul ne s'y risque qu'une fois sur trois). L'attaque est écrite dans `g.attacks` avec un compte à rebours de 3 minutes (`WAR_DELAY_MS` ; le jeu ouvert règle l'attaque à 10 secondes près avec `resolveDueAttacksNow`, et hors connexion le monde la règle au pas de 10 minutes suivant) : alerte dans le journal de la guilde, bandeau « Ta sentinelle de … est attaquée ! » partout dans le jeu et onglet « Défense » (attaquants, temps restant, défenseurs connectés). À l'échéance, sans toi, le combat est joué tout seul (`autoFight`, mêmes règles que le tien : la sentinelle et jusqu'à 3 membres connectés contre les attaquants) : les attaquants gagnent, la sentinelle disparaît et son or est partagé au hasard entre eux (les ressources sont perdues) ; les défenseurs gagnent, la sentinelle est intouchable 1 h. **Défendre toi-même** : le bouton « Défendre » suspend l'attaque (40 minutes au plus, `hold`) et lance un vrai combat où tu as pour alliés ta sentinelle (le moteur sait faire agir un allié comme un monstre : `actions` + `sentinel` sur le héros, `objective: "defense"`) et jusqu'à 2 membres connectés, contre les attaquants (monstres fabriqués comme les défenseurs, préfixe `attaquant_`). Tu gagnes si la sentinelle tient 12 tours ou si tous les attaquants tombent ; tu perds si elle tombe ou si ton héros meurt. « Quitter » en cours de combat ne règle rien : l'attaque se joue sans toi à l'échéance. Quand une attaque est réglée sans toi, un message s'affiche en haut à droite (vert si la sentinelle a tenu, rouge si elle est détruite ; `App.jsx` surveille la dernière ligne du journal de la guilde) en plus du journal. À venir : sorts à acheter (étape 3, peut-être inutile : les sorts se débloquent déjà avec le niveau de la guilde).
- **Les simulés ont leurs guildes** : un simulé qui a 13 000 or (niveau 10 au moins) en fonde une, les autres en rejoignent une selon leur caractère, donnent une part de leur or au-delà de 3 000, et le chef simulé dépense la caisse (palier d'abord, onglet sinon). Tout est rejoué à partir de l'heure comme le reste du monde (`sims.guilds`, rangé dans le marché du joueur). Ton activité (compteurs de quêtes) fait avancer les quêtes de ta guilde chaque minute (`syncPlayerGuild`). Le tag de guilde s'affiche au Classement.
- `scripts/test-guild.js` couvre les règles, les bonus, les simulés et les actions du joueur ; `scripts/simulate-guilds.js [fresh|generated] [jours]` simule des semaines pour régler l'équilibrage (rythme de niveau, caisse, paliers).

**500 simulés et leurs rôles** (`POPULATION_SIZE` dans `sim/population.js`, `traitsOf` et `shareOf` dans `sim/lives.js`) : chaque simulé a un *rôle* (combattant 32 %, récolteur 24 %, artisan 16 %, marchand 10 %, flâneur 18 %) qui règle la façon dont il partage ses séances entre combats, récolte et atelier, et un *profil* d'assiduité (60 % occasionnels, 30 % réguliers, 10 % acharnés). Les acharnés suivent une vocation : le chasseur d'xp passe 85 % de ses séances à combattre, le récolteur acharné 78 % à récolter, l'artisan acharné 75 % à raffiner et fabriquer. Passer à 500 coûte du temps de calcul au prorata (le rattrapage de 7 jours prend environ 6 s au total, fait par tranches de 12 pas, donc sans bloquer l'écran) ; une sauvegarde du monde des simulés faite avec une autre taille est refusée et recréée. Le colporteur reste nécessaire : mesuré sur 45 jours, les simulés seuls n'approvisionnent que les ressources de métier et de donjon, pas le butin de monstres. `node scripts/audit-global.js fresh 45` montre le détail par rôle et l'offre par rareté.

**Boss des simulés** (`sim/lifeBoss.js`, `sim/botFight.js`) : un simulé qui a le niveau conseillé (6 pour le Cavalier Déchu, 10 pour l'Épouvantail Ancestral, 18 pour le Veilleur Corrompu) tente un boss de temps en temps (au plus un par jour réel). Sa chance de victoire n'est pas inventée : elle vient du vrai moteur de combat, avec sa classe, son niveau, son équipement réel et son style de jeu (quelques combats d'essai, gardés en cache). Seul s'il est assez fort (≥ 75 %) ; sinon il cherche deux amis (70 % du temps) et à trois on gagne presque toujours, comme pour toi ; sans amis et trop faible, il attend de monter. Le butin est celui du jeu : xp et or du boss (xp qui s'effondre au-delà du niveau de la dernière région comme le reste), ressources rares (qui alimentent le marché, maintenant que le colporteur n'en vend plus), arme unique à 5 % pour sa classe (bonus de butin du groupe ×1,5, bonus d'xp du solo ×1,25). Chaque victoire alimente ses compteurs : il peut donc rendre les quêtes de chasse de boss et finir la chaîne (le Veilleur). Il équipe l'arme unique si elle vaut mieux que la sienne, et ses compagnons la portent au combat. Mesuré sur 60 jours : environ 20 armes uniques portées par les 200 simulés, 2/3 ont fini la chaîne de quêtes. Le rattrapage de 7 jours coûte environ 3 s au chargement (le moteur de combat est rejoué pour estimer les chances).

**Simulés au Manoir Englouti** (`sim/lifeDungeon.js`) : un simulé de niveau 20 et plus qui a gagné lui-même 3 Essences du Veilleur fabrique la clé (les lingots et l'ectoplasme manquants s'achètent à l'hôtel des ventes : `keyShopping` dans `simsShop`), puis tente le donjon avec deux amis (les deux autres classes ; 80 % du temps ils sont libres), au plus une fois tous les 2 jours. Il n'y va que si le vrai moteur lui donne au moins 30 % de chances d'en voir le bout (`dungeonOdds` dans `botFight.js` : les 4 salles à la suite avec PV reportés, quelques essais mis en cache ; la clé est consommée à l'entrée). Le butin est celui du jeu, salle par salle (xp, or, ressources exclusives, relique à 0,5 % portée dans son emplacement relique, bonus de butin de groupe ×1,5) : une expédition ratée garde les salles gagnées. Après un premier donjon fini, il vise le **palier 4** (`tierFor` dans `lifeCraft.js`) et achète les ressources du donjon à l'hôtel des ventes ; ses surplus y reviennent, ce qui approvisionne le marché en ressources de donjon (le colporteur n'en vend pas). Mesuré sur 120 jours : environ 370 expéditions et 320 réussites sur les 200 simulés (ils sont plus haut niveau que le donjon : le niveau 28 médian est atteint dès le premier mois). `test-simdungeon.js` vérifie la clé, l'expédition, le butin, la relique et le palier 4.

Étapes suivantes possibles : plus d'offre venant des simulés (moins du colporteur), le donjon du Manoir Englouti (il n'existe pas encore dans le jeu, donc ni pour toi ni pour eux), achats et ventes à l'hôtel des ventes, les inviter à te rejoindre en pleine carte, des vrais joueurs dans le groupe (serveur), l'IA des bots (parade, sorts de soutien).

Enchères à l'hôtel des ventes, vrais joueurs sur le même marché, joueurs simulés dans les régions, groupes et guildes, régions 2 et 3, emplacements d'équipement restants.

## Textures et décors des cartes (Ludo)

Les trois cartes de région n'utilisent plus d'aplats de couleur : le sol (herbe, terre) vient de textures qui se répètent sans couture (`public/assets/map/tex/`), et les arbres, rochers et arbres morts sont des sprites (`public/assets/map/deco/`), tous générés avec Ludo (style Illustration) puis assombris pour rester dans l'ambiance. Le thème de chaque région (`THEMES` dans `src/components/map/Terrain.jsx`) déclare ses textures (`tex`) et ses décors (`deco`) ; sans ces entrées, l'ancien dessin en SVG est utilisé. Le point d'entrée des villes et des autres cartes n'est pas touché.

### La ville fortifiée

Aldenmoor est dessinée par `src/components/map/CityTerrain.jsx` : remparts avec créneaux, tours d'angle et tours intermédiaires, trois portes (nord, ouest, est), sol pavé, place dallée autour de la fontaine, maisons dans les coins, tonneaux et charrettes. Textures et sprites Ludo dans `public/assets/map/citydeco/`. La grille de la ville (`buildCity` dans `maps.js`) n'a pas changé : mêmes obstacles, mêmes bâtiments, mêmes chemins pour le héros et les simulés.

## Bestiaire

Onglet « Bestiaire » du menu : tous les monstres (régions, mini-boss, donjon normal et difficile), listés à gauche par région, avec une recherche par nom de monstre **ou de butin**. La fiche montre l'image, la description, l'xp et l'or, les caractéristiques, les phases du combat (renforts, bonus d'attaque), chaque sort (PA, type, puissance, effet, fréquence ; les sorts de seconde phase sont signalés) et le butin. Les pourcentages du butin sont **ceux de ton personnage** : chance de base × (1 + bonus de butin) × bonus de groupe, plafonnés à 100 %, avec la base rappelée en petit. Le sélecteur Solo / Duo / Trio montre l'effet du groupe (×1,25 à deux, ×1,5 à trois) ; les butins à « taux fixe » (reliques) ne bougent pas, et les armes uniques sont marquées « réservées à une classe ». La logique est pure dans `src/utils/bestiary.js` (même formule que `rollRewards` du combat), l'écran dans `src/components/bestiary/BestiaryPanel.jsx`. `scripts/test-bestiary.js` vérifie, sur de vrais combats, que le taux affiché est bien le taux appliqué.

Le Bestiaire a un second bouton, **Équipements** : les 88 équipements du jeu (12 sets de 5 pièces par palier et par classe, armes, boucliers, anneaux, amulettes, capes, reliques ; les clés de donjon n'y sont pas). Chaque fiche donne les stats, le set avec le total de ses 5 pièces et ses bonus à 2 et 5 pièces, et la **recette** : métier, niveau requis, main-d'œuvre en or, chaque ressource avec la quantité demandée, ce que tu en as dans ton sac et **d'où elle vient** (raffinage avec l'origine des matières brutes, nœud de récolte, monstres avec leur taux de butin personnalisé). Les équipements qui ne se fabriquent pas (armes uniques du Veilleur, médaillons) listent les monstres qui les lâchent. La recherche trouve aussi un équipement par une ressource de sa recette. Logique pure dans `src/utils/gearbook.js` (vérifiée par `test-bestiary.js` : toute pièce a une recette ou un monstre, toute ressource de recette a une provenance), écran dans `src/components/bestiary/GearBook.jsx`.


## Skins des sets (apparence du héros)

Un set porté à 2 pièces ou plus change l'apparence du héros (ou on la choisit dans la fiche du personnage une fois une pièce du set possédée). Les trois premiers sets avaient leurs images ; les autres sont ajoutés un par un, à petit prix : l'**image de combat** (corps masculin et féminin) est générée avec Ludo (1,5 crédit par essai de 3 variantes), et les **animations de la carte** (marche, minage, abattage, cueillette) sont fabriquées gratuitement en recolorant celles de la tenue de base de la même classe avec `python3 -I scripts/recolor-hero.py <tenue>` (règles de teinte par tenue dans le script ; les feuilles et les métadonnées de `heroAnims.json` sont écrites toutes seules). Pour ajouter une tenue : image de combat dans `public/assets/combat/hero/{m,f}/<set>.png`, une entrée dans `OUTFITS` du script, puis le nom du set dans `HERO_OUTFITS` et `OUTFIT_LABELS` (`src/data/heroSprites.js`). `scripts/test-heroskins.js` vérifie que chaque tenue proposée a toutes ses images. Faits : Fossoyeur. À faire : Charognard, Brasier, Chevalier Déchu, Loup-Garou, Esprit Errant, Garde Noyé, Veneur, Veuve.
